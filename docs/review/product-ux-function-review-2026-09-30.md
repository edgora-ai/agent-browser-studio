# 产品、用户体验与功能审查问题清单

- 审查日期：2026-09-30
- 对象：Agent Browser Studio 1.0.1，`main` / `8f6b6d4`
- 方法：当前源码调用链核对、真实 Electron 交互、隔离数据验证、现有视觉审计、单元/冒烟测试；没有沿用旧审查文档作为事实依据。
- 交付范围：问题与建议，不包含业务代码修复。

## 总体评分：6/10

这是基于本次覆盖范围的专业启发式评分，不是用户调研、转化率或测试通过率的换算。

**结论：界面已具备较成熟的视觉一致性，但“用户选择会被尊重、执行状态可信、数据可以恢复”这三个基础承诺仍存在高影响缺口。下一轮应优先修复可靠性和首用闭环，而不是继续增加功能入口。**

### 优点

- Profiles、代理、Agent、自动化、运行记录、审计等功能基本形成完整工作台，而非孤立演示页面。
- 主要页面的布局、按钮层级、图标和明暗主题已形成一致体系；本次现有视觉审计的溢出、对比度、图标、选择器、文案检查均通过。
- 已具备错误重试、隔离配置、运行轨迹、审批、凭据脱敏、回收站及同步预览等基础机制。
- 测试基础较好：本次实际执行的单元/冒烟测试为 **1384 通过、1 失败**。但现有测试尚未充分覆盖下述跨模块与边界状态。

## 分级与证据说明

- **P1：发布前优先处理。** 涉及数据覆盖/恢复、非预期执行、核心功能阻断或用户控制失效。
- **P2：近期修复。** 明显损害关键流程、准确反馈或新用户成功率。
- **P3：体验与一致性修正。** 通常不独立阻断主流程。
- **真实复现**：操作当前构建的 Electron 或真实进程，获得结果。
- **逻辑复现**：运行原函数/前端逻辑的内存隔离探针，不等同于完整端到端验证。
- **代码确认**：核对当前实现的完整相关调用链；未在真实网络或故障环境中复现。

本次主清单共 **18 项：8 项 P1、8 项 P2、2 项 P3**。未确认 P0；这不代表已排除所有严重问题。

## P1：优先修复的功能与控制问题

### F01 — “保留本地”没有保护本地浏览器状态

**场景/复现路径：** 同一个已停止 Profile 在本地、远端都存在不同的站点存储或 Preferences；选择 `Local wins` 或逐项 `Keep local`，执行 Pull。

**当前行为：** 先导入 localStorage 并写入 Preferences，之后才计算配置元数据的合并策略。冲突选择并未约束前面的浏览器状态覆盖。

**影响：** 用户明确选择保留本地，却仍可能丢失本地站点状态。配置元数据和实际浏览器文件还可能来自不同版本。

**证据：** `src/main/services/sync-service.ts:349-401` 先写数据；`:409-445` 后应用策略。尚未对真实 S3 执行破坏性实验。

**建议/验收：** 在写入任何浏览器文件前生成统一、可预览的对象级应用计划；选择保留本地时，相关本地文件哈希和内容均应不变。同步失败应回滚或明确显示部分应用状态。

### F02 — 远端优先会移除本地已有的凭据

**场景/复现路径：** 本地保存带密码的代理或账号；Push 的快照脱敏后，再以 `Remote wins` 拉回同一对象。

**当前行为：** 上传记录不包含代理认证字段或账号密码；Pull 用远端整条记录替换本地对象，未合并保留本机专有的秘密字段。

**影响：** 即便用户只想同步名称、标签等元数据，也可能导致现有认证代理或账号填充失效。预览使用脱敏视图时还可能看不出这项损失。

**证据：** `src/main/services/sync-service.ts:1278-1309` 脱敏；`:418-445` 合并并保存；`:1493-1515` 远端记录整条替换。未实际拉取远端数据。

**建议/验收：** 区分可同步元数据和设备本地凭据；远端缺失秘密字段应表示“不参与同步”，而非“删除本机凭据”。增加 `保存凭据→Push→Remote Pull→实际解密/功能验证` 的往返测试，测试记录不输出密钥。

### F03 — 窗口聚焦/系统解锁会误判仍在执行的任务

**场景/复现路径：** 自动化长任务尚未结束；用户解锁、系统恢复，或在聚焦检查节流窗口之外重新激活应用。

**当前行为：** 调用用于进程启动恢复的 `reconcileAutomationState()`，把所有 `running` Job 更新为 `failed / interrupted by restart`。任务本身没有因此停止；普通 `markDone` 又只接受仍为 `running` 的记录。

**影响：** 真实执行与状态脱节；用户可能误判任务已停止或重复执行。带终态 Run 的部分记录可能在后续对账中修正，但不能消除中间的错误状态和其他动作类型的问题。

**证据：** `src/main/index.ts:386-400`；`src/main/services/automation-reconcile.ts:60-73,124-132`；`src/main/services/job-store.ts:203-208,277-284`。

**建议/验收：** 将“进程启动时回收死任务”与“运行期间重算时区/日程”分离。运行中进行锁屏/解锁、窗口切换后，Job 不应被标为重启中断，最终状态应与实际执行一致。

### F04 — 远期单次定时会因定时器溢出提前执行

**场景/复现路径：** 创建启用的 Once 任务，触发时间设为 30 天后。

**当前行为：** 将全部间隔直接传给 Node `setTimeout`。超过 `2^31-1 ms`（约 24.8 天）的延迟会被钳制为约 1 ms；此分支没有像 cron 分支那样分段等待。

**影响：** 用户认为安排在下个月的操作可能几乎立即执行，完成后还会消费这条单次任务。

**证据：** `src/main/services/automation.ts:704-716`；同文件 `:731-744` 的 cron 分支已有分段方案。Node 定时器行为已由内存探针验证；未创建有外部副作用的真实任务。

**建议/验收：** Once 复用分段计时，并在回调中重新核对绝对时间。覆盖 25 天、30 天、1 年以及系统时间变化，确保不会提前派发动作。

### F05 — 运行中记录可被删除，破坏执行与审计的关联

**场景/复现路径：** Agent 正在执行工具时，在 Runs 页面删除对应记录，或清空全部运行记录。

**当前行为：** UI 始终显示删除；服务端也没有活跃状态保护。删除会移除轨迹和成果绑定，但不会撤销已派发的工具操作。后续步骤及终态持久化找不到记录。

**影响：** 外部操作可能已发生，用户却得不到完整结果和审计；“删记录”意外影响正在执行的任务可靠性。

**证据：** `src/renderer/js/app/runs.js:342-358,535-552`；`src/main/ipc/agent.ts:450-455`；`src/main/services/agent-run-trace.ts:181-184,258-259,318-349`；`src/main/services/agent/desktop-chat.ts:219-235,276-295`。

**建议/验收：** UI 和后端同时拒绝删除活跃记录；提供独立“停止任务”操作，确认已终态并完成持久化后再删除。`clearRuns` 只清理终态记录并返回跳过数。

### F06 — 配置数达到上限，已有配置也被禁止启动

**真实复现：** 在独立用户数据目录连续创建 10 个测试配置；直接读取 `config.json` 确认 10 条，API 读回 10 条，按测试名前缀检索 10 条；然后启动其中一个已有配置。

```json
{
  "success": false,
  "error": "Trial profile limit reached (10/10). Activate a license for more — your data is untouched.",
  "code": "PROFILE_LIMIT"
}
```

**原因：** 新建和启动共用包含 `activeProfileCount() >= maxProfiles` 的许可判定。

**影响：** “允许最多 10 个配置”实际上变成“拥有 10 个后无法再启动任何已有配置”。带上限的其他套餐也使用同类条件。

**证据：** `src/main/services/license.ts:345-392`；`src/main/ipc/browser.ts:69-79`。测试证据：`/tmp/abs-product-review-20260930-7hmraL/license-cap-reproduction.json`。

**建议/验收：** 区分创建配额与启动许可。在数量正好等于上限且许可有效时，已有配置仍可启动；新增第 11 个才被拒绝。

### F07 — “拒绝并退出”只关闭窗口，后台仍运行

**真实复现：** 全新实例没有接受条款；点击“拒绝并退出”，页面关闭，随后本实例的 `/health` 仍返回 HTTP 200：

```json
{"status":"ok","service":"agent-browser-studio-api","mode":"gui","profiles":10}
```

**原因：** `termsDecline()` 调用 `window.close()`；应用另有保留托盘/后台服务的窗口生命周期逻辑。

**影响：** 用户以为已经拒绝使用并退出，后台服务却仍存活。调度器与服务的启动也早于条款接受。

**证据：** `src/renderer/js/app/wizard.js:82-85`；`src/main/index.ts:373-377,451-464`。测试证据：`/tmp/abs-product-review-20260930-7hmraL/terms-decline-reproduction.json`。

**建议/验收：** 使用明确的退出 IPC；拒绝后应用进程、监听端口及调度器全部结束。重新设计首次同意前允许启动的后台能力范围。

### F08 — Profile 备份恢复遗漏影响行为的元数据

**场景/复现路径：** 对开启 DRM、Web App URL、strict 渲染比例、指纹基线或扩展配置的 Profile 导出再导入。

**当前行为：** 导出使用的 `getProfileMeta()` 没有包含 DRM、Web App URL、renderScaleMode、指纹基线等；导入白名单又未接纳部分行为配置和扩展启用映射。即使导入支持某字段，上游导出遗漏仍无法完成往返。

**影响：** “导出成功/导入成功”不代表恢复了相同行为的环境；包括显示、网页应用入口、DRM 和扩展功能差异。

**证据：** `src/main/services/config-manager.ts:1124-1162`；`src/main/services/profile-archive.ts:96-141,152-174,193-209`。未执行真实浏览器会话备份。

**建议/验收：** 定义版本化备份 schema，列明不迁移字段并向用户展示；为所有可编辑行为字段建立导出→检查 archive→导入→读回→启动行为的往返测试。

## P2：近期应修复的产品与体验问题

### F09 — 回收站索引失败仍承诺可恢复

- **场景：** 移动 Profile 和更新配置已成功，回收站索引因权限或空间问题写入失败。
- **实际：** 索引写入只记录 warning；删除仍返回成功且审计写“recoverable for 7 days”。UI 只从索引生成回收站列表，因此找不到该条目。
- **证据：** `src/main/services/browser-manager.ts:376-400,403-459`；内存文件系统故障探针验证返回成功/列表缺项。未对真实磁盘制造故障。
- **建议：** 事务化移动、配置与索引，失败回滚；支持扫描恢复孤立目录。不要把“目录可能仍在磁盘上”描述成“用户可正常恢复”。

### F10 — 默认构建的许可模式在安装前不够清楚

- **实测：** `npm run build` 输出 `no public key in env — trial-only build`；界面显示“14 天 / 10 个配置 / 激活”。
- **代码：** 未注入公钥时，激活返回 `NO_PUBKEY`；到期会拒绝创建和启动。因此普通源码快速开始不是可直接长期使用或任意激活的发行方式。
- **证据：** `scripts/license-inject.mjs:21-24`；`src/main/services/license.ts:60-61,223-228,345-392`；`README.zh-CN.md:52-89`。
- **建议：** 安装前明确说明源码版、试用版、可激活发行版的区别，给出正确构建/发行入口；在不能激活的构建中解释原因，而非只展示激活按钮。
- **限定：** 不将 MIT 代码许可等同于应用必须免费，也不把 README 对“外部浏览器 license key”的表述直接解释成应用无授权限制。

### F11 — 默认建议任务与 Agent 实际能力不一致

- **真实界面：** Agent 推荐“启动一个配置并打开网站”；Automation 空态推荐对 Agent 说“每天9点启动demo”。
- **实际能力：** 桌面聊天过滤并拒绝 `launch_profile`、`create_automation_rule`；环境未运行时导航也不可用。聊天底部本身还写着“Agent 不会自动启动浏览器”。
- **证据：** `src/renderer/js/i18n.js:302,568,1536,1798`；`src/main/services/agent/desktop-chat.ts:173-180`；`src/main/services/agent/run-scope.ts:56-61,185-215`。
- **建议：** 示例由当前可用能力和环境状态生成；不能做的动作改为“一键转到对应界面”，不要通过放宽安全边界来迎合过时文案。

### F12 — 聊天草稿缺乏可靠保留

- **真实复现：** 输入未发送的需求→进入 API 配置→切回聊天，输入框由非空变为 `""`。
- **另一条逻辑确认路径：** 确实没有模型配置时，服务端在保存用户消息之前预检失败，而 renderer 已先清空输入和草稿；本次页面内存里的消息不等于后端历史已保存。
- **证据：** `src/renderer/js/app/agent-chat.js:66-70,182-193,307-327,806-881,933-952,1230-1231`；`src/main/services/agent/desktop-chat.ts:140-164`。
- **建议：** 对输入事件实时维护会话草稿，切换子页前保存；仅在提交确认后清空，预检失败将原文恢复到输入框或保留为明确的“未发送”消息。
- **验证限定：** 无模型配置场景只做内存逻辑验证。本次真实实例意外自动识别了宿主模型配置，不将那次发送当作“无模型配置”复现。

### F13 — 运行详情与列表可能显示过期终态

- **场景：** 打开正在运行的详情后等待结束；或连续刷新时较早请求较晚返回。
- **实际：** 事件刷新列表但不刷新已打开详情；乱序列表应答又可使较旧的 running 覆盖较新的 done。
- **影响：** 用户会看到过期的运行状态、验收结果和成果入口，不知道是否需要继续等待或重试。
- **证据：** `src/renderer/js/app/runs.js:249-287,504-520,785-841,877-896`；两条路径均经内存前端逻辑探针复现。
- **建议：** 详情订阅当前 run 更新；列表请求使用序号或取消机制；同一执行的终态不被旧快照倒写。

### F14 — 成功批次仍提示“重试全部失败”

- **逻辑复现：** 两条均为 done 的自动化运行组成一个批次，生成“重试全部失败 (2)”按钮。
- **原因：** UI 使用“所有可再次运行的终态记录”计数；后端批量失败重试只选择 error，成功批次点击后实际 `attempted=0`。
- **证据：** `src/renderer/js/app/runs.js:319-339,480-493`；`src/main/services/automation-retry.ts:38-49`；`src/main/services/automation.ts:392-424`。
- **建议：** 分开“重新运行全部”和“仅重试失败”；计数使用与后端完全一致的筛选规则。

### F15 — 首次引导中断后跳过已保存的检查点

- **场景：** 引擎已安装，完成创建第一个 Profile 后退出，但尚未进行启动/检测。
- **实际：** 重启先判断“已有 Profile”并返回，没进入恢复向导进度的逻辑。
- **影响：** 用户刚完成最基本的创建就失去后续成功验证路径；保存检查点并不等于流程可恢复。
- **证据：** `src/renderer/js/app/wizard.js:100-109,120-129,145-165,315-319`。
- **建议：** 优先处理未完成检查点，区分“创建过配置”和“完成首次成功启动”；在主页保留可恢复的首用进度。

### F16 — 回收站与磁盘故障备份概念混淆

- **实际：** 使用手册在磁盘故障备份建议中，将七天本地回收站与导出/S3 并列为可替代方案。
- **问题：** 回收站与 Profile 都在同一应用数据根目录，不能保护底层磁盘故障。
- **证据：** `docs/USER_GUIDE.zh-CN.md:139-143`、`docs/USER_GUIDE.en.md:139-143`；`src/main/services/browser-manager.ts:351-365`。
- **建议：** 分成“误删恢复”“应用迁移”“设备/磁盘故障恢复”三类，说明最后一类需要另一介质/设备/远端副本，并鼓励验证恢复。

## P3：一致性修正

### F17 — 侧栏版本号硬编码

实际构建与浏览器引擎页面“当前版本”为 1.0.1，侧栏一直显示 v1.0.0。`src/renderer/index.html:20` 写死版本；`package.json:3` 为 1.0.1；`src/main/ipc/app.ts:51-53` 已有真实版本接口。

## 产品改进建议（不计入 18 项已确认缺陷）

### S01 — 自动识别并使用本机模型配置需要明确的首次确认

这是有意设计的便利能力，不直接判定为凭据漏洞；但当前边界容易造成误解：`--user-data-dir` 并不会隔离 `os.homedir()/.claude/settings.json` 和环境变量，`getOrDetectLlmConfig()` 还会保存自动识别结果。

**本次真实观察：** 新数据目录仍自动识别宿主配置。一次只含审查占位文本的发送因此实际调用了模型。审查方已确认请求结束、停止后续联网验证，并删除本次临时数据目录中的配置与凭据副本。

**建议：** 首次导入前显示来源、端点和模型，要求明确确认；发送区持续显示当前提供商/模型；测试模式支持彻底禁用宿主配置发现。下次审查须同时隔离 HOME、环境变量和应用数据目录。证据：`src/main/services/local-agent.ts:30-67,84-111`。

### S02 — “始终允许”的授权粒度应以用户语言说明

当前数据库删除审批按动作和表名缓存，因此单行 DELETE 与无 WHERE 的 DELETE 可以共享许可。由于界面明确显示 Signature 且代码有意采用表级签名，本次**不将其报告为确定的权限绕过**。

**建议：** 将“始终允许”说明为“本会话对该表的所有删除”，对无 WHERE/批量破坏性操作保留单次确认，或收窄缓存范围。证据：`src/main/services/approval-gate.ts:105-119,132-161`；`src/renderer/js/app/approval.js:94-96`。

### S03 — 将首用路径从“功能目录”改为“完成第一个任务”

当前侧栏包含 12 个同层级入口，API 配置等关键准备又在 Agent 子页。对熟练用户合理，对新用户是否造成认知负担仍需要用户测试，不能仅凭页面数量认定缺陷。

**建议：** 提供“环境就绪→创建/启动配置→完成示例任务→查看结果→设置备份”的进度路径；SQL、团队、高级指纹等不必在首用阶段解释。围绕首次成功任务耗时、失败恢复率、任务完成后结果可理解性进行可用性测试。

### 条件性补充 — Firefox 的“已安装”标签未使用检测状态

`src/renderer/index.html:724-729` 的 Firefox 选项为固定文案；没有 Firefox 的主机上会失实。本机 `/Applications/Firefox.app` 确实存在，因此不能把本次截图当成“误报已安装”的动态复现。建议让选项由 `engineStatus` 驱动，并在未安装时提供安装/选择路径入口。
