PL-01 产品经理 业务闭环 / 结果正确性 批量启动谎报成功。bulkStart / batchStartSelected 用 setTimeout(i*500) 逐个调用 launch，不等待任何 launch 的 Promise，并在最后一个定时器里无条件 toast「N profiles started」。50 个里失败 20 个，用户看到的仍是 100% 成功。 用户 / 业务 P1核心操作返回系统性错误结论，用户带着「未启动」的 profile 进入后续流程；无数据丢失，故非 P0。 改为 Promise.allSettled + 并发上限（见 PL-02）；弹出聚合结果面板：成功/失败计数、失败清单（名称+原因+「定位到卡片」链接）、一键重试失败项；操作全程可中断。 ① 100 个 profile（其中 10 个代理不可达）批量启动，聚合面板在最后一个请求返回后 ≤1s 内出现；② 面板成功/失败数与 GET /api/profiles 实际状态逐条一致，误差 0；③ 失败项点击「定位」后滚动到对应卡片并高亮 2s；④ 一键重试后失败数单调不增。
PL-02 产品经理 异常与边界 / 并发 批量启动无并发上限与背压。客户端仅靠 500ms 错峰，无最大并发数；主进程的 concurrency 限流（automation.ts ≤16）只覆盖自动化规则，不覆盖手动批量启动。50 个 Chromium 冷启动会同时压满 CPU/内存，UI 表现为「假死」。 用户 / 系统 P1规模化场景（>20 profile）必然触发，资源耗尽导致整机不可用、用户无取消手段；新手小规模使用不触发。 UI 层与 IPC 层双层限流：全局并发 launch ≤4（可配置 1–8），队列可视化（排队中 x / 启动中 y / 失败 z），支持暂停与取消；单 profile 冷启动超 20s 自动标记失败并放行队列。 ① 100 profile 批量启动，ps 每秒采样显示并发 Chromium 进程峰值 ≤4；② 主进程 CPU 峰值 ≤90%、内存峰值 ≤8GB（M 系列 16GB 机型）；③ 主线程无 >200ms 长任务（Performance 录制全程）；④ 点「取消」后 ≤3s 内不再新增启动。
PL-03 产品经理 异常与边界 / 隐式副作用 检测类操作会隐式启动 profile。open-risk-check 在 profile 未运行时「auto-launches it first and waits for CDP readiness」（ipc/browser.ts:337），Drift / WebRTC 诊断同理。用户点「🔍 Check Risk」只是想看报告，却静默拉起一个浏览器进程（消耗资源、改变出口 IP 状态、可能产生风控行为）。 用户 / 业务 P1不可预期的副作用 + 无撤回入口，且发生在「检查」这类用户预期为只读的操作上；有手动关闭的绕过方案，故非 P0。 默认改为「需运行才检测」并给出一次性选择：「立即启动并检测（会自动启动该 profile）」/「取消」；已运行时不再提示；检测结束给用户「是否关闭刚启动的实例」的选项（默认保留）。 ① 对 stopped 的 profile 点击任意检测项，必须先出现含「将启动该 profile」文案的确认弹窗；② 选择「取消」时，进程数增量为 0，且不产生 launch IPC；③ 检测完成后 100% 出现「由本次检测启动，是否关闭」提示。
PL-04 产品经理 异常与边界 / 降级 代理失效无前置预检与归因。profile 绑定命名代理后被删除或健康检查失败时，卡片仅显示 proxy missing:<name>；启动失败的错误文案来自底层，不含代理名与最近一次健康检查时间，用户无法把「启动失败」归因到代理。 用户 / 业务 P2仅在代理异常时触发，用户可通过去 Proxies 页自查绕过；但归因成本高，定为 P2（若确认当前为「带病启动成功」则升级 P1，见 Q5）。 启动前做代理预检（复用 /api/proxies/health）；失败时错误必须携带：代理名、失败原因、最近健康检查时间、「前往修复」直达按钮；卡片上代理行对不健康代理加警示色。 ① 绑定不可达代理后启动，错误提示在 ≤300ms 内可见，且同时包含代理名 + 失败原因 + 上次检查时间；② 点「前往修复」≤2 步到达该代理编辑弹窗；③ 不健康代理在卡片上以 --danger 色显示，5/5 用户能识别。
PL-05 产品经理 需求完整性 / 业务闭环 风险检测结果一次性、不可回溯。Check Risk / Drift / Env / WebRTC 四个入口以 9px 小按钮藏在「Hardware」行末尾；结果只渲染在弹窗里，关闭即丢失，无「上次检测时间/结论」、无历史、不可导出。而 README 的 first-run 把「launch → 检查」定义为核心闭环。 用户 / 业务 P1核心闭环的产出不可留存，导致「风险治理」无法形成 PDCA；功能存在但等价于不存在，直接影响产品价值主张。 四项合并为卡片右上「健康检查」单一入口，一次跑完并输出 0–100 风险分 + 结论标签（安全/关注/高危）；结果写入 profile 记录，卡片显示「上次检测：3 分钟前 · 关注」，支持查看历史 N 次与导出 JSON。 ① 从卡片到看见结论 ≤3 步（点击健康检查 → 等待 → 结论）；② 默认全量四项检测 ≤15s（P95 ≤25s）；③ 结论在 7 天内可回溯（重开弹窗仍显示上次结果与时间戳）；④ 导出 JSON 可被 /api/profiles/{id}/drift 结构校验通过。
PL-06 产品经理 异常与边界 / 竞态 操作期无 busy 锁，存在启动/删除/编辑竞态。删除接口限制「仅 stopped 可删」，但 UI 未在 launch in-flight 期间禁用 Edit/Delete/Lock/Export；乐观覆盖 _profileRuntimeOverrides 5s TTL 内 running 状态可能失准，用户在此窗口点删除可能命中不一致状态。 系统 / 用户 P2需 5s 窗口内的快速连点才触发，属竞态而非必现；一旦命中会导致用户困惑或误删未停实例。 发起任一写操作后该卡片进入 busy 态：禁用所有写按钮 + 主按钮转 spinner + 卡片顶部细进度条；busy 期间点击给出「操作进行中」提示；操作结束统一由事件驱动解除。 ① launch 发起后 200ms 内点 Delete，按钮为 disabled 且产生 0 次 删除 IPC（spy 断言）；② busy 态在结果返回后 ≤200ms 解除；③ 连续 10 次快速点击 Launch，实际 launch IPC = 1。
PL-07 产品经理 需求完整性 / 失败闭环 引擎缺失的 fail-closed 未在 Profiles 页闭环。README 明确「未安装独立 Chromium 时启动 fail-closed 而非下载替代」，但：侧栏状态只在初始化调用一次（后续靠 tray 10s 刷新），且 Profiles 页本身没有「引擎缺失」提示与「安装/定位二进制」入口，用户只能从底层错误里猜。 用户 / 业务 P2仅影响首次安装/引擎被清理的用户，有文档可绕过（README Quick Start）；但这是新用户第一道门槛，转化损失显著。 Profiles 页顶部常驻引擎状态横幅（正常时折叠为一行小字）；缺失/版本不匹配时展开为警示条 + 「选择本地二进制 / 查看安装指引」按钮；Launch 前置短路检查，不再打到主进程。 ① 引擎缺失时打开 Profiles 页，警示横幅在首屏 ≤2s 内可见；② 从横幅到完成二进制选择 ≤3 步；③ 该状态下点击 Launch 0 次 启动 IPC，改为弹出引导。
PL-08 产品经理 需求完整性 / 引导 首次运行向导可永久跳过且无重入入口。dismiss 写入 localStorage 后即不再出现，设置页未提供「重新运行新手引导」（当前代码未见入口）；且触发条件为「无引擎 或 无 profile」二合一，已装引擎但 0 profile 的用户与全新用户看到同一套 4 步流程。 用户 P2只影响新用户与重装用户，老用户不受影响；可通过清 localStorage 绕过。 设置页新增「重新运行新手引导」；触发条件拆为三分支（缺引擎 / 缺 profile / 两者都缺），各自展示对应步骤；向导每步可跳过但保留进度条与「稍后完成」提醒。 ① 设置页存在入口，点击后 ≤2 步回到向导第 1 步；② 三种初始状态（fixture：无引擎 / 有引擎无 profile / 全新）分别命中对应分支，命中率 100%；③ 向导完成率埋点可查（依赖 TE-01）。
PL-09 产品经理 异常与边界 / 高危操作 批量删除的确认信息不完整。确认弹窗用 names.slice(0,5) 只列前 5 个名称，选中 50 个时用户看不到完整清单；且无「输入名称以确认」的高危保护，与删除（不可逆、含 cookies/localStorage）的后果不匹配。 用户 / 业务 P2需用户误操作才触发；删除后果不可逆（含站点登录态），但已有一次确认，故非 P1。 清单改为可滚动全量列表 + 「共 N 个，已显示 N/N」；数量 ≥10 时要求输入 DELETE 或勾选「我已知悉将删除 N 个 profile 及其站点数据」；删除后提供 7 天回收站。 ① 选中 50 个删除，确认弹窗显示全部 50 个名称（可滚动）；② ≥10 个时未勾选知悉项，确认按钮 disabled；③ 删除后回收站保留 7 天，一键还原成功率 100%（含 cookies/localStorage 校验）。
UE-01 终端用户 信息层级 单卡片信息过载、主次不分。一张 profile 卡同时承载：6 类 badge（running/lock/DRM/App/Firefox/tags）+ 9 个操作按钮（Launch/Stop/Edit/Cookies/Extensions/Export/Lock/Logs/Delete）+ 4 个检测按钮 + 1 个代理下拉 + 6 行 info-row；检测按钮字号 9px，低于可读下限，点击目标约 18px 高。 用户 P1每次使用都要在 13+ 个控件里找目标，是「每次都发生」的效率损失；无功能失效，故非 P0。 主操作保留 Launch/Stop/Edit/Delete 四个；Cookies/Extensions/Export/Lock/Logs 收进「⋯」溢出菜单；4 个检测项合并为「健康检查」（见 PL-05）；正文字号 ≥11px，图标按钮点击区 ≥24×24px。 ① 单卡一级按钮 ≤4 个，全部控件最小字号 ≥11px，点击区域 ≥24×24px；② 5 名用户在 10s 内正确说出「如何启动一个使用指定代理的 profile」的成功率 ≥4/5；③ 完成「新建→指定代理→启动」的点击数 ≤6 次。
UE-02 终端用户 视觉一致性 / i18n 硬编码中文导致 i18n 失效。index.html 至少 37 行含中文且未带 data-i18n（筛选栏「状态/标签/全部/运行中/已停止/清除筛选/全选可见」、批量条「N 个已选/启动选中/停止选中/分配代理/导出选中/删除选中」），切换到 EN 后仍是中文；profiles.js:103 的环境风险 toast 硬编码中文，与同一函数内的英文 toast 混排。 用户 / 业务 P1EN 用户每次进入 Profiles 页都会遇到中英混排，直接违背 README「zh-CN/en-US 双语文稿」的承诺，对外交付即被感知。 把上述字符串抽 key 进 i18n.js 并补 data-i18n；统一 toast 文案来源（禁止在业务代码里写字面量）；加 CI 检查拦截未带 key 的中文字符串（见 TE-07）。 ① EN 模式下遍历 #content DOM，中文字符数 = 0（自动化测试断言，排除用户自定义名称）；② zh-CN 模式下无未翻译英文残留（白名单 ≤0）；③ CI 新增 lint 规则，违规行阻断合并。
UE-03 终端用户 反馈与错误提示 Toast 单例且互相覆盖。toast() 先 remove() 已有节点再新建，3s 后自动消失，无 role="alert" / aria-live；启动成功 toast 会被紧随的环境风险 toast 直接覆盖，用户永远看不到第一条，错误也无留存。 用户 P1错误信息不可达 = 用户无法自愈，且屏幕阅读器用户完全收不到反馈；每次多事件操作必现。 改为可堆叠队列（最多 3 条，FIFO）；错误类不自动消失（8s 或手动关闭），带 role="alert" + aria-live="assertive"，含「查看详情」跳转；同一事件同步写入 Activity 页，Toast 只是镜像。 ① 连续触发 3 条 toast，3 条同时可见且顺序正确；② 错误 toast 从触发到 DOM 可见 ≤300ms；③ 缺 role="alert" 时单测失败；④ VoiceOver 可朗读错误文案（人工验证 1 次/版本）。
UE-04 终端用户 反馈与错误提示 / 表单校验 表单校验滞后且抛技术字段名。readHardwareFields 对非法整数直接 throw new Error("Invalid hardware value for hardware-concurrency")，最终以 toast 呈现技术字段名，未定位到具体输入框、未前置校验、未给出合法范围。 用户 P2仅在用户填错时触发，错误最终仍可见（可绕过：用户自行猜范围）；但技术字段名对终端用户零信息量。 字段级 inline 校验：失焦即校验，红框 + 「请输入 1–64 的整数」；提交时自动 focus 首个错误字段并滚动到可视区；错误文案零技术字段名，全部走 i18n。 ① 输入 abc 并失焦，≤300ms 内该输入框下方出现错误文案且 aria-invalid="true"；② 提交含 3 个错误的表单，焦点自动落在首个错误字段；③ 错误文案中出现技术字段名的实例数 = 0。
UE-05 终端用户 操作路径长度 首屏到「可用的 profile」路径过长。README first-run 为 7 步；Profiles 页头平铺 6 个按钮（New / Quick Create / Bulk Import / Import Backup / Start All / Stop All），无主次、无引导，新用户无从判断从哪里开始。 用户 / 业务 P2老用户不受影响，新用户首次转化率受损；有文档可绕过。 页头只保留 1 个主按钮「+ New Profile」+ 一个「⋯」（导入/批量收纳）；Quick Create 为默认路径并预勾「创建后立即启动」；空列表态用插画+一句话引导替代空白网格。 ① 新用户从冷启动到「第一个 profile 处于 running」≤3 步、≤60s；② 页头一级按钮数 ≤2；③ 空列表态引导点击率（依赖 TE-01 埋点）≥60%。
UE-06 终端用户 视觉一致性 状态语义混淆、无图例。「running」用边框高亮，而 Sync / Lock / DRM / App / Firefox 用同权重 badge 平铺，running 与 locked 视觉权重接近；无图例说明各 badge 含义，新用户需悬停逐个试。 用户 P3不改变操作结果，只增加认知成本；有 tooltip 可绕过。 状态分三层（生命周期 / 治理 / 能力），分别用边框色、图标、文字标签三种视觉通道区分；侧栏或页头提供可折叠图例。 ① 5 名用户无提示区分「运行中 / 已锁定 / 已同步」正确率 ≥90%；② badge 层级 ≤3 类，同类视觉通道一致（设计走查通过）。
UE-07 终端用户 交互连续性 列表刷新会打断用户操作。loadProfiles 用 innerHTML 整体重绘网格（软刷新 120ms debounce），任何一次启动/停止/切页都会重建全部卡片，正在聚焦的代理下拉、半勾选状态、滚动位置会丢失（交互层表现，根因见 TE-02）。 用户 P2在 >20 profile 且需要连续操作时频繁发生，用户可手动恢复，无数据损失。 改为 keyed 增量更新（以 dirId 为 key）；刷新前保存 scrollTop 与 document.activeElement 的标识，刷新后恢复；无变更时跳过重绘。 ① 对 100 个 profile 连续执行 10 次启动/停止，滚动位置偏移 = 0px，已勾选项 100% 保留；② 焦点在代理下拉时触发刷新，刷新后 document.activeElement 仍为该下拉；③ 数据无变更的刷新，DOM 变更节点数 = 0。
UE-08 终端用户 无障碍 / 可达性 图标按钮无可访问名称。🍪🧩📦🔒📋🗑 等仅用 emoji + title，无 aria-label；侧栏 role="tab" 缺少对应的 role="tabpanel" 关联；检测按钮无 aria-describedby。 用户 P3仅影响辅助技术用户，占比较小；功能仍可通过 title tooltip 使用。 所有图标按钮补 aria-label（走 i18n）；tab/tabpanel 用 aria-controls 关联；关键操作支持键盘可达（Tab 顺序与视觉顺序一致，Enter/Space 触发）。 ① axe-core 扫描 Profiles 页 严重/中等问题 = 0；② 所有可交互元素均有非空可访问名称（覆盖率 100%）；③ 纯键盘可完成「新建→启动→删除」全流程（无鼠标操作）。
TE-01 系统架构 埋点与监控 零产品遥测、零错误上报。全仓无 telemetry/analytics/Sentry/PostHog（grep 命中仅为 WebRTC 诊断字段）；渲染层仅 6 处 console.error 且不会落盘；启动成功率、耗时分位、功能使用率、崩溃率全部无数据，只能靠用户主动反馈。这直接导致本报告所有量化验收标准当前无法被测量。 系统 / 业务 P1不修复则任何性能优化与体验改进的收益都无法验证，且线上问题不可发现；属「能力缺失」而非「故障」，故非 P0。 本地优先的可观测性三层：① 结构化日志落盘（rotating，单文件 ≤5MB，保留 7 天，含 traceId）；② 本地指标（launch 成功率/耗时 P50/P95、检测耗时、IPC 错误数、批量队列深度）；③ 用户自持上报开关（默认关闭，端点可配）；设置页「诊断与遥测」面板 + 一键导出诊断包。 ① launch/stop/batch/检测 四类事件 100% 落盘且携带 traceId；② 本地指标面板可查 P50/P95，采样延迟 ≤60s；③ 导出诊断包 ≤10MB，明文密钥 grep 命中 = 0；④ 遥测默认关闭，开启需二次确认且可一键关闭并清除。
TE-02 系统架构 性能与并发 列表无分页/虚拟化，全量重建。loadProfiles 每次 innerHTML 整体重绘，无分页、无虚拟化、无增量 diff；100+ profile 时首屏与每次刷新都是 O(n) DOM 重建，DOM 节点数量级随 profile 数线性增长。 系统 / 用户 P1决定产品的规模上限；>50 profile 的重度用户（本产品目标客群）必然触发，且随使用时间必然恶化。 ≥50 条启用虚拟滚动或分页（每页 50）；以 dirId 做 keyed diff 更新；首屏先渲染可视区，其余空闲时补齐；为列表渲染加耗时埋点（依赖 TE-01）。 ① 200 个 profile 下列表首次渲染 ≤1.5s，滚动帧率 ≥55fps；② 无变更刷新 DOM 变更节点 = 0；③ 渲染期间无 >50ms 长任务；④ 1000 个 profile 下首屏 ≤3s（分页方案）。
TE-03 系统架构 接口依赖 / 韧性 IPC 无统一超时、取消与 traceId。agent 流有 120s abort、WebRTC 9s 超时、指纹采集 2s 超时，但 profile launch/stop/检测在渲染层只有 .then/.catch 裸调用，主进程阻塞时 UI 会永久停在无反馈状态，且无请求标识，日志无法串联。 系统 / 用户 P1主进程卡顿/引擎卡死场景下用户无自救手段（只能强杀应用），且与 TE-01 叠加导致问题不可诊断。 统一 IPC 封装：launch ≤30s、stop ≤10s、检测 ≤20s、列表 ≤5s 超时；每请求生成 traceId 贯穿 UI→IPC→service→日志；支持取消（AbortController）；按钮在飞行中禁用并展示已耗时。 ① 注入 30s 延迟 mock，UI 在 30s±1s 抛出可理解错误并提供「重试」；② loading 期间重复点击产生的 IPC 调用数 = 1；③ 任一条日志可按 traceId 串联 UI 与服务端（抽样 20 条，串联成功率 100%）。
TE-04 系统架构 接口依赖 / 隐私 风险检测硬编码依赖第三方站点且无确认。ipc/browser.ts:341 硬编码 https://ping0.cc/env：① 第三方站点改版/限流/不可达即功能失效（外部 SPOF）；② 会把该 profile 的完整指纹与出口 IP 发送给第三方，属隐私外发，但 UI 仅在 tooltip 一句话说明，无首次确认、无开关、无降级。 业务 / 系统 / 用户 P1隐私外发无告知（合规风险）+ 外部依赖无降级（可用性风险），且本地已有 Drift/Env/WebRTC 可替代，无需承担该依赖。 默认改为纯本地检测（复用 drift/env-risk/webrtc 三项）；外部站点检测降为可选项、需一次性确认并明示外发字段（指纹 + 出口 IP + UA）；URL 可配置；不可达时 ≤10s 内降级为本地检测并明确标注。 ① 默认路径下对非目标域名发起的请求数 = 0（网络日志断言）；② 开启外部检测前必须出现确认弹窗，文案含外发字段清单；③ ping0.cc 不可达（DNS mock）时 ≤10s 内降级为本地检测并标注原因。
TE-05 系统架构 数据流转 / 一致性 运行状态真相分散在三处。主进程 browser-manager 进程表、config.json 持久化、渲染层 window._profileRuntimeOverrides 乐观覆盖（5s TTL + seq 防串）三者无统一版本号与事件序列，靠 5s 定时回读兜底；UI / REST / MCP 并发写同一 profile 时可能互相覆盖（profile 级 lock 是否存在于所有写路径待确认，见 Q4）。 系统 P2单人 GUI 操作基本不触发；多客户端（REST/MCP/多窗口）并发场景才暴露，且后果为状态不一致而非数据丢失。 统一为带 version 的事件流（profile.status.changed），主进程为唯一真相源，渲染层订阅 diff；所有写操作带 expectedVersion，冲突返回 409 并提示刷新；乐观覆盖改为由事件确认驱动而非定时过期。 ① 并发 10 个 REST 写 + 10 个 UI 写，最终状态与最后一次成功写一致，脏写次数 = 0；② 冲突时返回 409 且 UI 弹出「已变更，刷新后重试」；③ UI 状态与 GET /api/profiles/{id}/status 一致性 100%（10 轮随机操作对拍）。
TE-06 系统架构 扩展性与可维护性 巨型模块 + 全局命名空间 + 无类型。主进程 local-agent.ts 135.9KB、rest-api-server.ts 100KB、browser-manager.ts 87.7KB、config-manager.ts 75KB；渲染层 8.8k 行 vanilla JS 靠 window.agentBrowser 全局串联，24 个模块均以 var toast = helpers.toast 方式重复解构（wizard.js 前 48 行全是解构），加载顺序耦合 script 标签。 系统 P2不直接影响用户，但显著抬高每次改动的回归风险与新人上手成本；属技术债，需排期偿还。 按「引擎生命周期 / 指纹 / 进程管理 / CDP」拆分 browser-manager；渲染层迁移 ESM + TypeScript（至少先补 api.d.ts 并开 tsc --noEmit）；helpers 改为模块 import；CI 增加单文件行数阈值。 ① 单文件 ≤1500 行（CI 拦截，超限阻断合并）；② 核心 service 单测行覆盖 ≥60%（先补基线，见 Q3）；③ 渲染层 tsc --noEmit 0 error；④ 新增功能平均改动文件数下降 ≥30%（以最近 10 个 PR 统计）。
TE-07 系统架构 可维护性 / i18n i18n 单文件全量加载且无 key 校验。i18n.js 79KB 一次性加载 zh/en 全量字符串，无按模块懒加载、无缺失 key 告警、无 zh/en 一致性校验。是 UE-02 硬编码中文问题的系统性根因。 系统 / 用户 P279KB 对本地桌面应用影响有限；主要危害是缺失 key 静默降级，与 UE-02 叠加。 按命名空间拆分（core/profiles/agent/…）；dev 模式缺失 key 显示 [miss:key]；CI 断言 zh/en key 集合完全一致 + 无未使用 key。 ① zh/en key 集合差异数 = 0（CI 拦截）；② dev 模式缺失 key 渲染为可见标记（截图验证）；③ 首屏 i18n 加载体积下降 ≥40%（拆分后按需加载）。
TE-08 系统架构 性能与并发 / 首屏 无性能预算与基准，验收无锚点。未定义首屏渲染、冷启动、列表渲染的耗时预算，也无 CI 性能回归门禁；本报告的耗时阈值均为建议值，需实测校准。 系统 / 业务 P2本身不是缺陷，但使所有性能类验收失去基线；属工程体系缺口。 定义并落库 5 条预算：冷启动到可交互 ≤3s、首屏列表 ≤1.5s、单 profile 冷启动 P95 ≤8s、列表刷新无变更 ≤100ms、IPC P95 ≤500ms（列表类）；接入 CI 性能冒烟（本地 fixture 100 profile）。 ① 5 条预算写入 docs/ 并在 PR 模板中列出；② CI 每 PR 跑一次性能冒烟，回归超 10% 即告警；③ 每次发版输出一份性能基线报告（P50/P95）。
TE-09 系统架构 性能与并发 / 节流 检测类操作无节流与并发上限。Drift / Env / WebRTC 会启动或复用浏览器做采集（WebRTC 单次 9s、指纹采集 2s），UI 连点即并发多个同类任务，批量场景下耗时与资源占用线性叠加。 系统 P3需用户连点或脚本调用才触发，单机场景影响有限；有等待即可绕过。 同一 profile 的检测串行化；全局检测并发 ≤2；按钮进入 loading 并禁用；重复点击合并为「检测进行中」提示。 ① 连点 5 次 Check Risk，实际执行次数 = 1，其余 4 次被吞并并提示「检测进行中」；② 全局并发检测任务数 ≤2（日志采样验证）。
没有匹配的问题，试试换个关键词或筛选条件。

2. Top 5 高优先级改进项

Top 1 · 建可观测性底座（TE-01）

P1 · 系统架构 · 埋点与监控 · 建议排在最前

当前零遥测、零错误上报，渲染层只有 6 处 console.error 且不落盘。这意味着：用户遇到启动失败我们不知道、性能退化我们看不见、本报告里所有量化验收标准当前无法被测量。

  • 结构化日志落盘（rotating，≤5MB/文件，7 天，带 traceId）
  • 本地指标面板：launch 成功率、耗时 P50/P95、IPC 错误数、批量队列深度
  • 可选外发遥测：默认关闭，端点自持，二次确认
  • 一键导出诊断包（≤10MB，密钥已脱敏）
预期收益：把「无法度量」变成可度量，线上问题从「等用户反馈」变为分钟级定位（MTTR 降低一个量级）；并为 Top2–Top5 提供验收数据来源。它是其余四项的前置依赖。

Top 2 · 批量操作的正确性与并发治理（PL-01 + PL-02）

P1 · 产品逻辑 · 结果正确性 / 并发

批量启动现在「发射后不管」：不等待 launch 结果，无论成败一律 toast「N profiles started」；且无并发上限，主进程的限流（≤16）只覆盖自动化规则，不覆盖手动批量。

  • Promise.allSettled 收集全部结果 + 并发上限 ≤4 + 队列可视化
  • 聚合结果面板：成功/失败计数、失败清单（名称 + 原因 + 定位）、一键重试
  • 支持暂停、取消；单项超时 20s 自动失败并放行队列
预期收益：消除「谎报成功」这一信任杀手（运营场景最常见的批量操作）；峰值并发进程从 N 降到 ≤4，100 profile 批量启动从「卡死」变为可预期；失败定位时间从「人工逐个点」降到一次点击。

Top 3 · 反馈系统重构（UE-03，含 UE-04）

P1 · UI 与交互 · 反馈与错误提示

Toast 单例互相覆盖（启动成功会被紧随的环境风险提示直接顶掉），无 role="alert"/aria-live，错误 3s 自动消失且无处可查。用户收不到错误 = 无法自愈。

  • 可堆叠队列（≤3，FIFO）；错误类不自动消失
  • role="alert" + aria-live="assertive"；含「查看详情」跳转
  • 事件同步落 Activity 页，Toast 只作镜像
  • 配套：表单改为字段级 inline 校验，错误文案零技术字段名
预期收益：错误信息可达率从「部分」到 100%，减少「启动失败不知道为什么」类工单；顺带解决无障碍与校验体验，改动量小、影响面覆盖每一次操作，性价比最高。

Top 4 · 检查类操作的副作用与外部依赖（PL-03 + TE-04）

P1 · 产品逻辑 + 系统架构 · 隐式副作用 / 隐私外部依赖

两个问题叠加在同一入口：点「Check Risk」会静默启动未运行的 profile（用户以为只是只读检查）；检测本身硬编码访问 https://ping0.cc/env，把该 profile 的指纹与出口 IP 发给第三方，无确认、无开关、无降级。

  • 默认走纯本地检测（drift / env-risk / webrtc 三项已具备）
  • 外部站点检测降为可选项：一次性确认 + 明示外发字段 + URL 可配
  • 需启动才能检测时，先弹确认并说明「将启动该 profile」
  • 外部不可达 ≤10s 内降级为本地检测并标注原因
预期收益：同时消除合规风险（隐私外发无告知）、可用性风险（第三方 SPOF）与不可预期的资源副作用；本地检测更快（目标 ≤15s）且不依赖外网。

Top 5 · 列表性能与刷新不打断（TE-02 + UE-07）

P1/P2 · 系统架构 + 交互 · 规模上限

列表每次刷新 innerHTML 全量重建，无分页/虚拟化/diff。直接后果：规模上不去（100+ profile 掉帧），且每次启动/停止都会打断用户正在进行的勾选、滚动与下拉焦点。

  • ≥50 条启用虚拟滚动或分页（每页 50）+ dirId keyed diff
  • 无变更刷新跳过重绘；保存并恢复 scrollTop 与 activeElement
  • 配套 TE-08：确立 5 条性能预算并接入 CI 冒烟
预期收益：把可用规模从「几十个 profile」提升到「数百个」；消除高频操作中的交互中断感。这是重度用户的留存放大型问题——用户 profile 数只增不减。

紧随其后（下一批）：UE-02（i18n 硬编码中文，EN 用户必现）、PL-05（风险检测结果不可回溯）、PL-07（引擎缺失无引导）、TE-05（状态三处真相，多客户端并发脏写）。
