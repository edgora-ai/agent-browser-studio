# rev13 Android 隔离模拟器性能实测（2026-11-17）

## 结论

**没有复现三标签切换后无法滚动、切换后画面不再更新的卡死，但不能判为“性能完全没问题”。**

- rev13 与 rev12 都完成同一轮交互矩阵：每版注入 **60 次标签切换、80 次滑动、10 次总览开关**；5 个阶段终点仍为 3 个标签且能正常响应。3 个页面在测试前、后都通过文本位置变化的滚动见证。次数是输入尝试，不是逐次视觉验收。
- rev13 测量窗口的浏览器 PID/包名范围日志未发现崩溃、ANR 或历史 `kGestureScrollBegin`/`render_input_router` 断言；7 个采样进程身份保持稳定。这是有界观察，**不是历史问题已彻底修复的证明**。
- 停在 ping0 不操作时，rev13 浏览器进程组仍消耗约 **89% 的一个 CPU 核心**；rev12 同场景约 92%。热点主要在 privileged/GPU 相关进程与页面 renderer，不在管理器进程。需要关注持续渲染/资源加载及模拟器图形路径，不能直接归罪于新历史存储代码。
- 原生窗口的保留帧记录存在长尾：切换/混合场景 p95 约 20.6–20.8ms，总览 p95 约 24.3ms、最大 124.3ms。**这些是浏览器外壳，不是网页 FPS，也不是输入到显示的延迟。**
- 短时全进程 PSS 未显示持续单调增长；不足以证明没有泄漏。单轮对照无法宣称 rev13 有确定百分比提升或不存在退化，总览 CPU 的 rev13 单次值反而更高。

## 4. CPU / PSS 单轮对照

**100% = 占满一个核心，而不是四核整机的 100%。** CPU 汇总所有 `com.ahoo.abs.browser*`，包括管理器、`:browser`、privileged、独立 UID renderer 和 `_zygote`；以 `/proc/PID/stat` 的 utime+stime、CLK_TCK=100 和实际首尾采样时间计算，按 PID+startTicks 区分身份。约 2 秒采样一次。PSS 每个唯一 PID 只计一次，是阶段前后快照，不是峰值或均值。

| 阶段 | rev12 平均 CPU | rev13 平均 CPU | rev12 PSS 前→后 MiB | rev13 PSS 前→后 MiB |
|---|---:|---:|---:|---:|
| 静置 | 92.00% | 89.08% | 477.95→467.54 | 476.88→412.35 |
| ping0 滚动 | 85.76% | 84.63% | 469.04→478.59 | 413.85→383.50 |
| 30 次纯切换 | 53.38% | 51.10% | 479.50→501.39 | 383.17→408.48 |
| 30 次混合切换 | 64.59% | 62.85% | 477.53→477.12 | 384.60→390.11 |
| 总览 10 轮 | 113.83% | 122.40% | 467.77→480.23 | 380.31→389.89 |

rev13 的完整约 2 秒采样区间峰值分别为 118.50%、94.92%、78.24%、105.30%、136.68%。纯切换另有一个仅 0.749s 的尾段得到 117.42%，不混作约 2 秒峰值。两种口径及实际时间均保存在原始 JSON/CSV。

两版每阶段均观察到 7 个稳定进程身份，无采样报错、已观察到的进程更替或缺失；所有 PSS 端点完整。瞬时未被采到的进程仍可能漏算。

rev13 静置 CPU 细分：`:privileged_process0` 48.18%、ping0 renderer 37.35%、`:browser` 3.53%，其他进程接近 0。privileged 进程的 `MESA exportSyncFdForQSRILocked` 日志在不操作时仍频繁出现，是图形后端持续活动的证据，**不是某个应用代码根因已被证明**。

主机 QEMU 平均 CPU 与来宾应用 CPU 分开：rev13 五阶段分别为 159.67%、179.57%、120.10%、157.12%、205.90%。不能相加为“浏览器 CPU”，也不能当作真实手机负载。

对照限制：每版只有一轮，rev13 与 rev12 的预热时长、环境数据/缓存、网络加载时点不同；rev12 为新装后的独立测试环境。相近数值是描述，不是统计意义上的改善/无退化证明；总览阶段 rev13 的单次 CPU 更高。三张短历史页面也不构成大历史库写入压力测试。

### 4.1 关闭重追踪后的静置复核

为排除“只是 Perfetto 重采集导致高 CPU”，在同一模拟器用不启动 Perfetto、不采集 FrameTimeline、关闭 SurfaceFlinger timestats 的轻量 `/proc` 采样，分别将静态 A、ping0、再静态 A 置前台，各约 20 秒。后台标签保留。

rev12：静态 A **0.05%** → ping0 **86.23%** → 静态 A **0.05%**。主机 QEMU 相应约 9.31% → 151.80% → 8.96%。说明这一版本的高活动与 ping0 前台状态相关，不能只用重追踪开销解释；隐藏后可降下来，不像所有后台标签持续全速运行。

rev13：静态 A **0.84%** → ping0 **90.12%** → 静态 A **0.15%**；主机 QEMU 相应约 11.40% → 157.29% → 10.97%。7 个进程身份稳定、采样完整。此复核使用同证书 rev13 覆盖安装到一次性 rev12 环境，保留 `perf-comparison` 的磁盘资料，正常管理器入口重建 3 个运行时标签；不是重新运行一整套冷启动对照。

两版的高活动都与 ping0 在前台相关，隐藏后大幅下降；重追踪不是充分解释，也没有证据说明是所有隐藏标签一直忙循环。rev13 轻量 ping0 中 privileged 约 48.98%、renderer 约 37.53%、`:browser` 约 3.57%。**“未操作”不等于网页负载已静止**；这里仍有不完整加载的公网文档，无法仅凭这些数据区分页面动画/加载与图形后端实现成本，也不能把两次约 20 秒样本的差值当作版本退化百分比。

## 5. 渲染证据与质量门槛

[Perfetto FrameTimeline 文档](https://perfetto.dev/docs/data-sources/frametimeline)明确说明不支持 SurfaceViews。这里 Chromium 网页使用 `SurfaceView[...NativeBrowserActivity](BLAST)`，因此下表只能描述**原生应用窗口/浏览器外壳**，不能充当网页 FPS、网页掉帧率或点击到显示延迟。

| rev13 阶段 | 正时长窗口记录数 | non-None 标记（含 Unknown） | App Deadline Missed | 时长 p50 / p95 / max ms |
|---|---:|---:|---:|---|
| 静置 | 不可用 | 不可用 | 不可用 | 不可用 |
| ping0 滚动 | 1 | 1（Unknown 1） | 0 | 17.806 / 17.806 / 17.806 |
| 纯切换 | 1,680 | 1,662（Unknown 10） | 52 | 9.487 / 20.752 / 63.538 |
| 混合切换 | 1,722 | 1,705（Unknown 7） | 49 | 9.416 / 20.624 / 58.626 |
| 总览 | 467 | 465（Unknown 0） | 19 | 9.599 / 24.301 / 124.340 |

时长为 doFrame 开始到 GPU 完成/buffer post 较晚端点，**不是 CPU 执行时长或最终呈现延迟**。non-None 大量包含 Prediction Error、Buffer Stuffing，不能把其比例直接叫可见卡顿率。

采集并未全项达标，不能隐去这些失败：

- 静置输入运行了 60 秒，但对应 trace 仅有 3.497 秒边界、进程匿名且没有浏览器调度/图层覆盖。静置 Perfetto CPU/帧数据为 **UNAVAILABLE，不是 0**。独立 `/proc` 60 秒采样仍可用。
- 滚动/纯切换/混合 trace 的 buffer0 overwritten bytes 原始计数为 **16,089,088 / 6,946,816 / 230,490,112**；discarded chunks 原始计数分别为 1/2/3，总览为 4。这些计数可能累计，不擅自当作阶段增量。
- 所以保留的 sched CPU、帧数与时长分布都是**不完整保留窗口的观察**，不代表全阶段；尤其不能用 mixed 的残存调度 CPU 来反驳 `/proc` 全窗口 CPU。
- SurfaceView legacy timestats 有非零帧记录，但 `totalTimelineFrames=0/jankyFrames=0` 是缺少覆盖，**不是零掉帧**。`--latency` 是有界 128 槽历史环，不换算为全阶段 FPS。
- rev12 没有运行重 trace 解析；没有做两版帧指标优劣对比。

## 6. 稳定性、测试中断与保留失败

rev13 定时矩阵起始至套件完成窗口，去重后共 29,907 条日志，其中 24,511 条在采样浏览器 PID/包名范围；未匹配崩溃/ANR/历史输入断言。原始连续 logcat 覆盖整个 rev13 窗口，其退出 255 发生在之后的 rev12 UI 设置阶段。

rev12 五个输入窗口去重后共 20,237 条日志，未匹配浏览器崩溃/ANR/死亡标记。无日志标记并不能排除一切故障；检查范围及覆盖端点保存在 JSON。rev13 测量前没有另采 activity exit-info，不补造历史退出原因。

保留的问题记录：

1. 第一次 rev13 trace 输出选了 `/data/local/tmp/`，被 Perfetto 权限拒绝；尚未运行定时矩阵。保留失败及已成功的 3 个前置滚动见证，改用系统支持的 `/data/misc/perfetto-traces/` 后 `rev13-run2` 完成全部矩阵。
2. rev12 UI 设置脚本曾把“可见输入框数量”假设写错，安装后断言退出；修正可见字段条件，从已打开的对话框继续，没有重复重置应用。
3. 随后一次 UIA 导出返回空，同时原 logcat 流退出 255。核实仍是同一 QEMU PID、同一来宾启动，后续只观察即见正常 1 标签总览；**没有重启模拟器或把它算作应用 ANR**。保留中断证据，恢复串流后通过普通 UI 补齐两页，再完整执行 rev12 矩阵。原因未归属，不能硬说完全没有工具中断。
4. 首个 trace_processor 下载端点不可达，改用官方备用 HTTPS 主机，未绕过 TLS；分析程序及 SHA 已记录。早期汇总脚本缺少匿名静置进程字段报错亦保留，修正后 5 个 SQL 查询均 rc0。

5. 最终清理的 `adb emu kill` 在隔离 HOME 下返回控制台 token 不匹配（命令自身 rc0，但响应 KO，被断言识别）。没有更改认证 token 或安全策略；重新核实专用 QEMU 的 AVD/PID 后，仅向该自建进程发送 SIGTERM。其启动包装器随后正常退出 rc0，专用 logcat 与 loopback 夹具服务也已停止。此为清理工具问题，不混入性能测量结果。

最终复核再次确认两个 APK、5 份原始打包收据与 36 个冻结源输入未变，模拟器内最终安装 APK 的 SHA 与 rev13 候选一致；`git diff --check` 通过、索引为空。证据/独立 AVD 文件保留，没有删除用户数据。

## 8. 后续优先级

1. **首先定位 ping0 前台持续 renderer/GPU 活动**，区分页面动画/加载、原生合成与模拟器图形后端；现有证据只把问题缩小，尚未证明具体源代码根因。
2. 总览/切换仍有原生窗口长帧信号，后续要用无丢失、开销可控且能覆盖 Chromium 内容的采集，再谈是否满足流畅性门槛。
3. 完整 ping0 负载、多轮冷/暖测试、大历史库与真机功耗不在这次已验证范围内。本次不把“没复现卡死”包装成 Chrome 同等流畅、零掉帧或完全修复。

**最终判定：有界功能场景完成；存在持续活动与长帧的性能风险信号；完整渲染性能验收未通过证据门槛。**
