# Agent Browser Studio 产品优化方案

- 日期：2026-09-19
- 状态：M1 已实现并通过 macOS 主路径的目标验收，详见 [M1 实现与验证记录](m1-execution-control-validation-2026-09.md)；M2–M4 仍为方案，未实施。
- 范围：Agent 任务执行、结果交付、自动化状态、首次业务成功体验。
- 基线：本次产品检查所见的当前工作区，包含上一轮尚未提交的可靠性修复；不能只按 Git HEAD 重新开始开发。
- 定位：这是下一阶段的产品方案，不替换 [历史改进路线图](improvement-roadmap.md) 或 [2026-08 产品评审](review/product-review-2026-08-29.md)。历史文档中的部分缺口已经修复，不作为本方案的现状依据。

## 1. 目标与原则

### 1.1 核心目标

把现有的浏览器、Agent、模板、调度、数据库和运行记录，串成一条用户能够理解、控制和验收的任务流程：

> 选任务 → 填参数 → 选环境 → 检查前置条件 → 执行与停止 → 验收结果 → 导出 → 再次运行或设为定时任务。

用户在任何时刻都应知道：**正在操作什么、能不能停止、究竟完成了什么、失败后怎么办。**

### 1.2 本轮设计假设

- 优先服务技术型个人及互信小团队，场景限于自有站点、内部系统和明确获得授权的网页任务。此定位是设计假设，不是用户调研结论。
- 保持本地优先，复用现有 Electron、服务层、审批、任务与存储体系，不另建云平台。
- 优先验收 macOS Apple Silicon 当前主路径；其他平台按实际验证结果声明支持，不将配置可构建等同于安装包可用。
- 聊天先做好单次运行绑定一个浏览器环境；批量编排继续使用现有自动化能力，不在首轮新增聊天多环境并行。
- 原有 Profiles、代理、账号、数据库、REST/MCP 的专业能力保留，不为新手流程删除高级入口。

### 1.3 实施原则

1. 先补控制与真实状态，再补成果交付，最后优化引导与规模化。
2. 能复用现有能力就不再建一套：已有向导、模板、审批、任务重试、轨迹、后台运行和导出服务。
3. 用户界面表达的限制必须由主进程执行层强制实施，不能只靠提示词或隐藏按钮。
4. 停止不等于回滚，重试不等于断点续跑，运行结束不等于业务验收通过。
5. 本轮不做大规模视觉重设计；沿用现有组件、图标、双语体系与导航。

## 2. 制定方案时的基础与缺口

| 方向 | 已有基础 | 当前需要补齐 |
|---|---|---|
| Agent 执行 | 聊天、工具调用、审批、技术超时与轮数上限 | 显式环境范围、聊天停止入口、准确的结束原因 |
| 结果记录 | 持久化运行、步骤、参数与结果、数据库 | 回答到本次运行的直达入口、业务成果视图、搜索筛选与导出 |
| 重试恢复 | 自动化失败重试、失败运行重试入口 | 解释重试范围和已发生的影响；聊天没有同等流程，不能宣传为通用续跑 |
| 定时任务 | once/cron/event、持久化 jobs、并发控制、重试、托盘/headless | 已错过/下次执行/等待重试等状态、终态提醒、恢复后的状态对账 |
| 首次上手 | 四步配置向导、错误说明和修复入口、现有模板 | 引导用户完成第一个可验收的业务任务，而非只完成配置 |
| 数据安全 | 只读查询、会话失败保护、配置字节预算、轨迹事务保护 | 新增结果与导出功能继承这些约束，不重新引入静默覆盖或假成功 |

本次产品检查主要是代码与交互路径核对，没有新增真实用户访谈或生产使用统计。上一轮通过的测试属于可靠性修复基线，不构成本方案新功能的验证结果。

## 4. M1：先让 Agent 可控、可追踪

### 4.1 环境选择

- 聊天输入区顶部展示本次操作环境的名称、运行状态；默认不隐式选择“第一个正在运行的环境”。
- 未选环境时允许普通问答及原有受保护的非浏览器能力，但不开放浏览器操作；需要操作时给出明确的选择入口。
- 可以记住上次选择，但下一次发送前仍须清楚展示，并重新验证环境是否存在、是否可用。
- 环境未启动时展示独立的“启动所选环境”操作，由用户明确启动并沿用现有启动检查和权限约束；模型不自动启动环境。
- 一次运行开始后固定其环境范围；用户切换其他页面或准备下次任务，不改变正在执行的运行。
- 环境被删除、停止或失去权限时明确失败，不静默切到其他环境。

**后端边界：**每次浏览器工具派发都校验目标属于本次运行范围，窗口/页面/CDP 目标必须从该环境解析；复合工具不得绕过检查。不能证明其作用范围受限的全局或任意脚本工具，在受限运行中不开放。HTTP、文件、SQL 等非浏览器能力继续遵守各自审批和路径限制；选择一个环境不是扩大其他权限的授权。

此项不等于修复了所有 REST/MCP 团队权限问题，也不把环境范围当作完整的多租户隔离承诺。

### 4.2 停止与生命周期

- 运行中将发送操作替换为清晰的“停止”，展示当前动作和已耗时。
- 点击后立即显示“正在停止”，主进程确认取消意图；禁止继续派发新步骤。
- 将取消信号传到支持取消的模型请求、工具调用和等待逻辑。
- 不能中断的已发出操作，保留“正在等待当前操作结束”的状态，并受该工具超时约束；结果无法确认时明确提示，不伪装成已经撤销。
- 取消中的审批请求作废，不能稍后批准后继续运行；不影响其他运行的审批。
- 已发生的提交、发送、文件写入等外部变化不会自动回滚，结果页必须保留已知影响。
- 关闭窗口仍按现有规则隐藏到后台，不将其等同于停止；真正退出/异常退出后的运行标记为中断，不自动重放有副作用的动作。

**实现约束：**

1. 主进程维护运行上下文，至少关联 runId、streamId/请求 ID、conversationId、发起窗口、环境范围和取消信号。
2. 在首个工具动作之前发送运行已创建事件，让前端提前获得 runId；不能等整个 chatStream 返回才知道取消目标。
3. 处理取消早于启动确认、重复取消、结束后取消等竞态；取消请求必须校验发起方与运行归属。
4. 同一会话的重复发送不得产生重叠执行；重复请求与正在执行的不同请求要有明确响应。
5. 流式片段结束不是整个任务结束；终态以执行层提交结果后的事件为准，晚到的片段不得把终态改回运行中。
6. 复用现有执行入口和工具能力，不为聊天重新实现一套自动化队列。

### 4.3 运行结束与业务验收分开

采用“两层状态”，避免用一个成功徽章承载所有含义。

| 层次 | 建议表达 | 用途 |
|---|---|---|
| 执行生命周期 | 运行中、正在停止、已结束 | 表示执行过程是否仍在进行 |
| 结束原因 | 自然结束、用户取消、超时、达到轮数上限、进程中断、执行错误 | 回答为什么结束 |
| 业务验收 | 未验收、通过、部分通过、未通过 | 回答用户目标是否达成 |

兼容策略：保留现有 running/done/error 对外字段，在运行元数据中增补结束原因与验收信息。自然结束仍可映射为 done；取消、达到上限、超时、中断、执行错误不映射为业务成功，旧状态按兼容规则映射为 error。自动化 job 已有的状态由适配层解释，不为 UI 强行重写为聊天状态。

旧记录没有验收证据时显示“执行结束 · 未验收”，不追溯改写为“任务成功”。步骤失败后被模型恢复，不必一律判整个任务失败；最终业务结论由实际验收证据决定，而不是统计是否出现过任意工具错误。

M1 只落实准确的结束原因与“未验收”默认状态；模板验收器在 M2 交付。

### 4.4 回答与运行关联

- 每次执行对应一个可持久化的运行引用，在聊天消息旁提供“查看本次运行”。
- 页面刷新、切换会话、重启后仍能找到同一运行；同一会话多次执行不能串到最后一条记录。
- 历史运行已经清理或超出保留范围时，显示“运行记录已清理”，保留聊天内容，不显示空白或假结果。

建议交互结构，非当前界面截图：

```text
环境：内部测试站点 A ▼       状态：已运行
任务：检查指定页面并生成报告

正在执行：读取第 2 个页面       已耗时 00:18     [停止]

执行结束 · 未验收 / 结果已验收
摘要、未完成项、已发生的影响                    [查看本次运行]
```

### 4.5 M1 验收门槛

- 同时存在环境 A/B，选择 A 后，模型请求操作 B 必须被执行层拒绝，B 的页面与数据保持不变。
- 未选环境不得执行浏览器操作；HTTP、文件、SQL 等独立能力仍受原有审批与访问边界保护。被删除或失效的环境不能触发隐式替换。
- 分别在模型请求中、工具执行中、等待审批中、启动确认前取消；主进程确认取消后新派发的步骤数为 0。
- 重复发送、重复取消、完成与取消同时发生，不产生重复执行或两个互相矛盾的终态；另一会话不受影响。
- 轮数上限、超时、取消、异常退出均显示真实结束原因，不显示“已验收成功”。
- 用独立 userData 执行、读盘、重启、按会话和 runId 检索，确认环境、结束原因、消息关联完整保存。

## 5. M2：交付可验收、可使用的结果

### 5.1 最小业务验收

先选一个低风险、可用本地 fixture 回归的现有模板，补成完整样板，再扩展其他模板。

- 每个样板模板声明输入、目标范围、输出结构、成功条件和可能的副作用。
- 检查实际产物：文件存在且可读、记录数量符合要求、必需字段有效、指定页面断言通过等。
- 不把模型自然语言中的“已完成”当作验收证据；无法自动确认的条件显示“待人工确认”。
- 例：预期 20 条记录，18 条通过、2 条失败，显示“部分完成 18/20”，列出失败项与原因，保留有效结果。
- 自由聊天默认未验收；不承诺对任意自然语言任务自动判断真实业务成功。

### 5.2 在现有 Runs 中提供结果页

不新增一套重复的任务中心。扩展现有运行详情，形成三层信息：

1. **结论层：**环境、任务、耗时、结束原因、验收结果、完成/失败数量。
2. **成果层：**表格、文件、截图或报告预览；标记是否完整、生成时间和对应运行。
3. **诊断层：**步骤时间线、参数/结果、错误详情，默认折叠较长技术信息。

列表优先支持任务名称、时间范围、来源、环境、结束原因和验收结果筛选。先在现有保留容量内实现，不预先引入全站全文搜索系统。

### 5.3 导出与数据边界

- 首批支持运行摘要 JSON 和结构化表格 CSV；文件类成果按原文件类型保存。PDF、自定义报表编辑器暂不做。
- 运行元数据导出与业务成果导出分开。现有 exportData 能复用部分元数据能力，不等于已经具备完整业务结果导出。
- 导出前显示运行、字段、条数、是否部分结果和保存位置；若存在截断或数量上限必须明确展示。
- 业务成果必须绑定 runId/数据集范围，不通过导出整个共享表来替代“导出本次结果”。
- 诊断与默认导出遵守脱敏规则，不带密码、Cookie、密钥或认证头；CSV 防公式注入，页面预览对不可信内容进行转义或隔离。
- 导出只保存到用户选择的本地位置，不自动上传；文件访问继续做路径范围检查。

### 5.4 结果存储与再次运行

- 运行元数据只保存有限长度的摘要、验收信息、成果引用。图片、长表格和文件正文不放进 config.json。
- 新增成果存储封装：按运行绑定受控目录中的文件或带运行归属的数据集；保存后校验完整性，再公开可用状态。
- 无论采用文件还是 SQLite 数据集，都必须测试写失败、磁盘不足、索引提交失败与重启后的对账；不承诺 JSON 配置和 SQLite 之间存在原子跨库事务。
- 显示结果占用和保留策略。空间不足时明确拒绝并保留原数据，不靠静默删除用户成果满足预算。
- 首版提供“再次运行”，明确它会创建新的执行；沿用既有自动化重试能力。
- “只重试失败项”仅对能识别独立条目、证明重试范围且副作用安全的模板开放；涉及提交/发送等动作必须有幂等措施或人工确认。
- 聊天任意工具序列的检查点续跑不在本阶段范围内。

### 5.5 M2 验收门槛

- 全部成功、部分成功、全部失败、没有验收器四类 fixture，显示结论与实际数据逐条一致。
- 表格预览与导出行数、字段、内容一致；结果达到导出上限时不能声称“全部导出”。
- 两次运行写入同一业务表时，只导出选中运行的数据，不混入其他运行或环境的结果。
- 写入 → 直接查询 SQLite/读取成果文件 → 关闭重开 → 服务读回 → 按 runId 检索，内容与归属一致。
- 非法路径、公式型单元格、不可信 HTML、敏感字段 fixture 均被正确处理。
- 取消或失败后的有效部分成果仍可查看；再次运行不覆盖原运行及其结果。

## 6. M3：定时任务状态真实、结果可知

### 6.1 状态与下次执行

- 将“规则启用”与“当前执行状态”分开显示。
- 显示：下次执行时间、时区、当前排队/执行/等待重试、最后一次结果。
- 对已过期且没有有效待执行工作的 once 规则，显示“已错过 · 需要重新安排”，提供重新安排和停用入口。
- 状态来自调度器及相关 job，不只比较前端日期。排队中、执行中、等待有效重试的 once 不能误判为已过期。
- 按规则版本/本次计划关联 job；历史测试运行或旧版本成功记录不能冒充当前计划已经执行。
- 首版不自动补跑错过的任务；重新安排时显示新的执行时间与时区，不把现有“测试运行”按钮冒充消费 once 的正式补跑。
- 休眠恢复、系统时间/时区变化、应用重启后重新对账。进程未退出时已挂起的回调与重启后未安排的过期规则分别测试，不因增加徽章静默改变调度语义。

### 6.2 完成、失败与待处理提醒

- 前台展示可返回结果页的通知；后台可启用系统通知，提供静默/关闭选项。
- 只对最终逻辑执行通知一次，中间重试不反复弹失败提醒；重启不重发历史通知。
- 系统通知不展示敏感业务内容。用户拒绝通知权限时保留应用内记录，不影响任务执行。
- 明确说明运行边界：关窗会隐藏并继续运行；真正退出后不再调度，机器休眠期间不承诺准时执行。

### 6.3 M3 验收门槛

- 未来 once、已错过 once、排队、重试等待、取消、成功禁用、用户停用分别显示正确状态。
- 真正到时的 once 只执行一次，重启后不重复；仍覆盖上一轮已修复的消费/重试生命周期。
- 规则修改、手动测试、旧 job 不污染新计划的下次时间和完成判断。
- 时区与夏令时边界、休眠恢复和系统时间变化有确定性测试及目标平台实测。
- 通知点击进入对应运行；重启不重复通知，拒绝权限后功能仍可用。

## 7. M4：让新用户完成第一项业务任务

### 7.1 复用配置向导，增加任务引导

- 保留已有引擎、环境、启动检查、AI 配置向导；完成后进入“运行第一个任务”，而不是重新建一套安装流程。
- 首批打磨不超过三个授权场景：自有站点巡检、内部后台表格整理、测试环境流程回归。
- 每个模板提供示例输入、预期成果、耗时影响因素和权限/外发说明；提供本地演示数据以便无真实账号试用。
- 明确区分 mock 演示与真实模型执行。演示通过不能作为真实 LLM 任务成功率证据。
- 正式执行前检查引擎、环境、模型配置、必要授权、输出位置和基本存储可用性；错误就地提供修复入口。
- 完成后直接展示结果和“再次运行/设为定时任务”，而不是只展示祝贺提示。

### 7.2 帮助与交付口径

- 在任务创建、失败详情、环境/模型缺失处提供上下文帮助，说明原因和下一步操作。
- 统一说明支持平台、后台运行边界、产品试用限制、引擎要求和数据存放位置。
- 明确“本地存储”不等于“所有数据不离开本机”：任务内容可能按执行需要发送到用户配置的模型服务或目标站点。
- 诊断包先预览并脱敏，再由用户选择本地导出；不自动上传，不引入默认开启的远程遥测。
- 原生安装包、签名/公证、引擎和辅助程序架构必须分别验证，未测的平台标注未验证。

### 7.3 M4 验收门槛

- 缺引擎、缺模型配置、环境失效、输出位置不可写时，都有明确原因和对应修复入口。
- 用干净 userData 从启动到模板结果再到本地导出跑通，不依赖开发者预置的个人配置。
- zh-CN/en-US、键盘操作、窄窗口、空结果与错误状态均走查；新增文案不破坏图标或现有布局。
- 邀请 5 名未参与开发的目标用户完成样板任务，记录每一步阻塞点，不用开发者熟练操作代替上手验证。

## 9. 验证与发布门槛

### 9.1 自动化与真实数据验证

1. 为每个缺口先补能在旧实现上失败的回归，再实现功能；不只断言按钮存在或 mock 返回成功。
2. 受影响单测、完整 unit + smoke、类型检查、隔离完整构建、i18n/文件大小检查通过。
3. Electron E2E 使用独立 userData、本地 fixture 与 mock LLM；不调用个人账号，不发送真实业务数据，不升级依赖来掩盖失败。
4. 数据写入后直接检查物理 JSON/SQLite/成果文件，再从服务读回、重启、按 runId/会话/条件检索；拒写场景逐字节确认旧数据不变。
5. 若扩展 REST/MCP，公开入口、无认证拒绝、合法认证、作用域拒绝及审批均端到端验证，不为了测试绕过 UI 审批策略。
6. 覆盖取消竞态、跨会话隔离、等待审批、超时/轮数上限、错误传播、旧数据兼容、部分成果与导出归属。
7. 对新增页面和弹窗做 zh/en 差分视觉检查与键盘走查；动态内容和异常状态同样覆盖。
8. 清楚列出通过、失败和未执行项；桌面验证不代替容器或跨平台安装包验证。

### 9.2 产品指标

以下均为建议的首轮验收目标，不是当前已达到的成绩。性能在固定设备、数据量和网络条件下测量；达不到时先解释与修正，不通过改口径制造达标。

| 指标 | 测量口径 | 建议目标 |
|---|---|---|
| 环境范围正确性 | A/B 隔离 fixture 中越界浏览器动作的实际执行次数 | 0 次 |
| 取消有效性 | 主进程确认取消之后新派发的步骤数 | 0 次 |
| 停止反馈 | 固定本地测试环境中，点击到 UI“正在停止”、到主进程确认的 P95 | 分别 ≤200ms、≤1s；不承诺不可中断动作在此时间内结束 |
| 结果准确性 | 受控模板验收状态与实际产物对拍 | 全部一致，假成功 0 次 |
| 历史可追踪性 | 重启后消息链接、runId、环境和成果归属抽样对拍 | 全部一致；已清理记录明确提示 |
| 首次成功时间 | 引擎与模型可用后，开始样板任务到获得可导出结果 | 目标 ≤5 分钟；安装下载及模型延迟单独记录 |
| 独立完成能力 | 5 名目标用户，无开发者代操作完成样板任务 | 至少 4/5；属于可用性试验，不外推市场成功率 |
| 实际使用效果 | 模板验收通过率、人工介入次数、再次运行比例 | 先建立基线，再设改善目标，不捏造当前数据 |

指标默认从本地运行记录和用户同意的试验记录计算，只记录必要信息。没有验收器的自由聊天不计入“业务验收通过率”；取消与未验收分别统计，不隐藏失败来提高成功率。

## 10. 暂不做与风险控制

本方案首轮不做：通用可视化工作流编排器、任意 Agent 工具链的自动续跑、云端控制台、企业级组织治理重构、新的浏览器内核/规避检测能力、模板商城扩张、全平台同时宣称正式支持、全量 UI 框架迁移。

后续候选：

- 模型 token/费用显示与预算：只使用可核实的 usage 和价格口径，缺失时显示未知，不用 0 冒充免费；硬限制能力需按供应商验证。
- 安全检查点续跑：先为少量幂等模板定义输入快照、检查点和恢复条件，再推广；不能从任意中断位置重放有副作用的步骤。
- Trace 增量存储：单独设计迁移、失败恢复、保留策略与性能验证，不与所有 UI 变更捆绑一次发布。
- 平台交付：按平台验证安装、引擎、辅助程序架构、签名和升级路径，再扩大支持范围。

主要风险及处理：

| 风险 | 控制方式 |
|---|---|
| 只在 UI 上限制，工具执行仍越界 | 主进程逐次校验目标，复合工具同样受约束，无法约束的能力不开放 |
| 停止按钮只停止显示，后台仍继续 | 真实取消信号和派发屏障；已发出操作单独说明，不承诺回滚 |
| 模型自称完成导致假成功 | 执行结束与业务验收分层，按实际产物验证 |
| 重试重复提交或发送 | 默认再次运行明确告知；局部重试限幂等模板或人工确认 |
| 成果继续撑大 config.json | 元数据限长、正文独立存储、保留字节预算与拒写保护 |
| 扩展状态破坏旧记录/客户端 | 保留旧字段，增补原因与验收信息；缺字段默认未验收 |
| 把历史路线图当作当前事实 | 实施前核对当前代码与测试基线，不重复建设已经存在的功能 |
| 方案无限扩张 | 每轮只交付一个里程碑；额外架构迁移单独评估与批准 |
